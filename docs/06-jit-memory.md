# 06 — JIT memory (W^X)

Generated bytes in a `std::vector` are just data. To *run* them they must live
in memory the CPU is allowed to execute.

## What `JitBuffer` does

```cpp
mmap(nullptr, size, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
memcpy(pages, code.data(), code.size());
mprotect(pages, size, PROT_READ | PROT_EXEC);   // now executable, no longer writable
reinterpret_cast<int64_t(*)()>(pages)();        // jump into it
```

Three properties matter:

1. **Page granularity.** `mmap` works in pages, so the size is rounded up to a
   multiple of `sysconf(_SC_PAGESIZE)`.
2. **W^X (write xor execute).** The pages are *never* writable and executable at
   the same time. Mapping RWX would work on most systems but is exactly the
   pattern exploit mitigations target; some platforms (hardened Linux, macOS on
   Apple Silicon, iOS) refuse it outright. Doing the flip correctly is both good
   practice and the portable path.
3. **RAII ownership.** The destructor `munmap`s; the class is non-copyable.
   Leaking executable pages in a long-running JIT is a real bug class.

## Calling into generated code

```cpp
using Fn = int64_t (*)();
reinterpret_cast<Fn>(memory_)();
```

The cast is the whole trick: a pointer to bytes becomes a pointer to a function.
It only works because the generated code obeys the platform's calling convention
— it must leave its result in `RAX` and end with `ret`
(see [docs/07](07-calling-convention.md)).

## Things that bite

- **Forgetting `ret`.** Execution runs off the end of your code into whatever
  follows. `Emitter::finish()` appends `C3` so this can't happen.
- **Instruction cache coherency.** On x86-64 the i-cache is coherent with
  writes, so no explicit flush is needed. **On ARM64 it is not** — a
  `__builtin___clear_cache` call is required. Worth knowing before the ARM64
  stretch goal.
- **`mprotect` failing.** Some hardened environments deny `PROT_EXEC`.
  `JitBuffer` reports the `errno` message rather than crashing.
- **Empty buffers.** Mapping zero bytes is rejected explicitly.

## Later milestones

Once there are multiple functions (M4), each gets its own buffer (or one buffer
with recorded offsets) so `call rel32` can compute the distance between them.
That's also when a small "code space" allocator starts to be worth having.
