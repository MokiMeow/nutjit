# ADR 0003 — Target x86-64 / System V only (for v1)

**Status:** accepted · **Date:** 2026

## Context

A JIT emits instructions for one architecture and obeys one calling convention.
Supporting several from the start multiplies the backend work and the testing
surface.

## Decision

Target **x86-64** with the **System V AMD64** ABI (Linux / WSL2) for v1. ARM64
is a documented stretch goal, not a v1 requirement.

## Rationale

- x86-64 + System V is the most documented combination (Intel SDM,
  felixcloutier, the ABI spec), so every byte can be checked against a primary
  source and disassembled with `objdump`.
- One target keeps the encoder small enough to read in one sitting — the point
  of the project.
- The architecture already separates concerns: the lexer/parser/AST know nothing
  about x86, so a second backend is an additive change (a new `codegen`), not a
  rewrite. That makes ARM64 a genuine stretch goal rather than wishful thinking.

## Consequences

- **Does not run natively on Windows** (different ABI) or on ARM machines —
  WSL2 is the supported path on Windows, and CI must use an x86-64 runner.
- An ARM64 backend would additionally need explicit instruction-cache
  invalidation after writing code (`__builtin___clear_cache`), which x86-64 does
  not require — noted in [docs/06](../06-jit-memory.md) so the stretch goal
  doesn't start with a silent bug.
